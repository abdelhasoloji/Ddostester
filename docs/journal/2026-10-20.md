## Efficiency workstream

### Increment 1 — fast commit gate and short loop

- `.githooks/pre-commit`: prettier + eslint on the staged files, then a full typecheck.
  Enabled `core.hooksPath .githooks` (it was configured by `npm prepare` but not active).
  `SKIP_TYPECHECK=1` for doc-only commits, `git commit --no-verify` in an emergency.
- `scripts/verify-touched.mjs` and `npm run verify:touched`: format/lint only on changed
  files, full typecheck, then `vitest --changed` in both workspaces.

Why: two CI runs this week were red on issues a 20-second hook catches — prettier on files
I never opened, and a mock type intersection. The loop between edits was 4 minutes, which
encouraged skipping it.

Measured: the hook adds ~25 s to a commit; `verify:touched` is seconds when one module
changes, and falls back to the full suite when a shared file like `package.json` changes
(vitest treats every test as affected, which is correct).

### Increment 2 — the DRS loop runs in CI

`scripts/qa/drs-e2e.mjs` builds a frozen measured plan and drives the real orchestrator,
generator and probe collector against a loopback target: 15 s, no database, no build step.
It asserts FINAL_REPORT, at least one sealed proof, a PARTIAL assessment and the
generator+user evidence points. `npm run test:drs` runs it and CI gained a `drs-e2e` job.
Verified green on the PR (drs-e2e pass) and merged as #254.

### Increment 3 — pre-push stops duplicating CI

The hook ran `verify:fast` on every push: lint, typecheck and both suites, four to five
minutes, for work CI repeats five minutes later. With the pre-commit gate in place, pre-push
now runs the repository-wide lint and typecheck only (~30 s) and leaves the suites to CI.
`PRE_PUSH_FULL=1` keeps the old behaviour.

Measured: a push now costs about 30 s instead of 4–5 minutes, in a session that pushed
eighteen times.

Verified against the report of a real measured run: two A4 pages, gaps legible, no

### Increment 7 — entry and origin witnesses

The evidence declared entry and origin unrepresented because no independent observation
existed. `probe-collector` now reads two optional counters around the exposure — an edge
witness and an origin witness — and seals `entry` and `origin` points with the rate each one
actually observed over the window. When a witness answers, the corresponding dimension is no
longer listed as unrepresented.

`scripts/qa/witness-target.mjs` provides an instrumented target: an edge in front of an
origin, each with its own counter, deliberately two so the evidence cannot report one number
for both. The e2e script drives the edge, passes both telemetry endpoints, and asserts
`points=entry,origin,generator,user` plus the absence of the two dimensions in
`unrepresented_dimensions`.

The verdict stays PARTIAL, and must: the load, source diversity and persistence requirements
are still not met. What changed is that the evidence now _observes_ the exposure instead of
declaring it unobserved — which is the difference between a prototype and an assessment.

Deployment wiring: `DRS_ENTRY_WITNESS_URL` and `DRS_ORIGIN_WITNESS_URL` on the service.

### Increment 8 — scoped access instead of root

Two forced-command keys replace root for ordinary work: `ddostester_deploy` runs only `status`
or `deploy` (the production update script), and `ddostester_sql` runs one statement as a
read-only role with a statement timeout. Both wrappers live in `/usr/local/sbin` and log to

Verified: `status` returns the health JSON; `rm -rf /` is refused; `select count(*)` returns

### Increment 9 — the product gets its domains

Production is `drs.trustena.lu`, staging is `testdrs.trustena.lu`. `deploy/enable-domains.sh`
refuses to touch Caddy while either name points elsewhere, then appends one site block per
name, validates, reloads and waits for `/health` on both.

The config was validated against a copy of the live Caddyfile (`Valid configuration`), so the
syntax is proven before any reload. It is deliberately not enabled: both names still resolve
to `51.178.16.135`, and ACME failures would only burn retries.

Posture: the product domains use application authentication over Let's Encrypt TLS. The
client-certificate `:443` block stays for the operational estate; a client cannot present a
certificate from this CA.

### Increment 10 — the client address behind the proxy

Fastify ran without `trustProxy`, so behind Caddy every request would have appeared as
`127.0.0.1`: the audit trail and the login throttle would both have recorded the proxy instead
of the client. The app now trusts `X-Forwarded-For` from a loopback peer only
(`TRUST_PROXY`, default `127.0.0.1`), which is exactly the hop Caddy occupies.

Two tests use Fastify inject with an explicit peer address: a loopback peer with the header
yields the client address, a non-loopback peer with the same header is ignored. Trusting every
peer would let a client choose the address the audit records, so the narrower default matters.

### Phase 1, increment 2 — the dossier screen and client creation

The Clients list now links to a dossier: signed scope (reference, ceiling, authorised targets),

### Phase 2 — the campaign wizard, and capacity stops authoring plans

The wizard is four steps and the mode is the second one, on purpose: it decides what the
campaign can prove, so it is chosen with the target in view rather than buried in a form. Step 1
picks a dossier and a target from its signed scope (free text only without a dossier), step 2
picks measured or synthetic amplifier, step 3 takes level, exposure, baseline, rate, assertion
and rationale with the live envelope, step 4 summarises, requires the attestation and freezes.

Capacity keeps what it is good at — calibration, envelope, reachability — and links to the
wizard instead of embedding a second, divergent plan form. Verified in Chrome on staging: the
target pre-filled from the dossier, the synthetic mode selected, the plan frozen, redirect to
Assessments, zero console errors.

### Phase 3, increment 1 — the synthetic amplifier really measures its own output

A synthetic-lab plan now runs: the process opens a loopback sink it owns, drives the engine at
the declared budget for the exposure, and counts what reaches the sink. The validation carries
claimed versus produced rate, produced concurrency, a fidelity ratio, four controls (rate,
concurrency, plan digest, motivated exclusions) and a sealed hash. The revision ends in
`ENGINE_VALIDATED` — no assessment, no verdict, and `certification` never enters the picture.

The report recognises it: a sealed synthetic run renders a SYNTHETIC / NON-CERTIFYING page with
the claimed-versus-produced table and the controls, and a synthetic-lab plan that has not run yet
still renders as a frozen plan.

Two tests: the run measures, seals and produces no verdict; a measured plan is refused.

### Phase 3 screen + phase 4 — one assessment screen, two truths

`/assessments/:id` renders a revision: header with the mode badge, the state trace as a timeline,
and then either the measured assessment or the synthetic validation.

Measured: verdict, observation points (source, observed load, samples, artifact hash), legitimate
transactions, and the archived requirements with required versus recorded. Synthetic: the
claimed-versus-produced table, fidelity, the four controls, and the explicit statement that no
traffic reached the target and no verdict was produced. The DRS list links each row to it.

Frontend 518 tests, coverage 80.36 %.
